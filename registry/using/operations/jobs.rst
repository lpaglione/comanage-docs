Background Jobs
===============

.. sidebar:: On this page

   .. contents::
      :local:
      :depth: 1

:bdg-success:`New in v5`

Registry **Jobs** are processes designed to run asynchronously and handle
operations that are too large or time-consuming for a single web transaction
— syncing records, reconciling group memberships, reprovisioning, processing
deletions, and similar batch tasks. Jobs are also the mechanism for automating
recurring work on a schedule.

In v5, Jobs can be queued, monitored, and canceled directly from the Registry
interface — no server console or container access required. This is a
long-requested capability; in v4, all job management required typing commands
on the server or configuring containers directly.

For the full technical reference, see
`Registry PE Jobs <https://spaces.at.internet2.edu/spaces/COmanage/pages/256934706/Registry+PE+Jobs>`_
in the Technical Manual.

1. Managing Jobs in the Interface
-----------------------------------

:bdg-success:`New in v5`

Jobs are accessible to CO Administrators via **CO > Jobs**. From this view,
administrators can:

- **Queue a Job** — trigger a supported Job Plugin to run immediately or
  schedule it for background processing.
- **Monitor Job status** — see whether Jobs are Queued, In Progress, Complete,
  or Failed, along with start and end times.
- **Cancel a Job** — stop a Job that has been queued or is in progress.
- **View Job History** — review the detailed output generated by past Jobs.

Not all Job types can be triggered from the interface — some are only run
via cron or the command line. See the plugin-specific documentation for
details on which triggers each Job Plugin supports.

For background processing, a cron job should still be configured to invoke
the Job Command at appropriate intervals, even when Jobs are queued through
the interface. See the
`New Registry Setup <https://spaces.at.internet2.edu/spaces/COmanage/pages/243074640/New+Registry+Setup>`_
page in the Technical Manual for cron configuration guidance.

2. How Jobs Work
-----------------

When a Job is triggered — either from the Registry interface or by an external
scheduler — it is placed in a queue. The Job Command processes queued Jobs
sequentially for a given CO, in the order they were queued. It is not
currently possible to prioritize Jobs relative to one another.

A Job can be run **synchronously** (immediately, from the command line) or
**asynchronously** (queued for background processing via cron).

3. Job Status
--------------

A Job moves through the following statuses during its lifecycle:

- **Queued** — the Job has been registered and is waiting to be processed.
- **Assigned** — a queue runner has claimed the Job and is preparing to run it.
  The assigned host and process ID are recorded.
- **In Progress** — the Job Plugin has been invoked and is actively running.
- **Complete** — the Job finished successfully.
- **Failed** — the Job encountered an error and did not complete successfully.

4. Canceling Jobs
------------------

A Job in **Queued**, **Assigned**, or **In Progress** status can be canceled by
viewing the Job artifact in the Registry interface and clicking **Cancel**.

- If the Job is in **Queued** status, the cancellation is immediate.
- If the Job is in **Assigned** or **In Progress** status, cancellation is
  a request — the invoked Plugin determines when to actually stop processing.

5. Job History
---------------

Registry records Job history in two places:

- **High-level Job status** — the start time, end time, and final status for
  each Job, viewable via the Registry interface. Only CO Administrators can
  view Job history.
- **Job History Records** — detailed transaction or task records generated
  during Job execution. These may be linked to specific Person or External
  Identity records and can be viewed from the appropriate Person canvas for
  authorized viewers. Each Job Plugin determines what level of detail to
  record.

Job History is also written to the Registry trace log. This behavior may
change in a future release.

6. Available Job Plugins
-------------------------

The specific operations available as Jobs are determined by which Job Plugins
are activated in your deployment. See :ref:`extend-plugins` for information
on activating plugins, and the Technical Manual's
`Available Job Plugins <https://spaces.at.internet2.edu/spaces/COmanage/pages/301367456/Available+Job+Plugins>`_
page for the list of Job Plugins included with Registry.

7. Changes from v4
-------------------

- **Jobs can now be managed through the Registry interface.** In v4, all job
  management required logging into the server and running commands in the
  console, or updating container configuration directly. In v5, CO
  Administrators can queue, monitor, and cancel Jobs entirely through the
  Registry UI — no server access required. This was one of the most
  frequently requested capabilities from the v4 community.

- **Job queue processing** was introduced in v5.0.0. Jobs are queued and
  processed via the Job Command, allowing Jobs from multiple sources to be
  handled in a consistent order.

- **As of v5.2.0**, a single queue runner no longer processes Jobs in parallel
  (though multiple queue runners may still be launched). This change improves
  reliability and predictability of Job processing.

- **The SQL Assigner Job Plugin is new in v5.2.0.** It assigns identifiers
  or email addresses to CO Persons by querying an external SQL database,
  drawing on a configured SQL Assigner Identifier Assignment. This plugin
  has no direct v4 equivalent. See the Technical Manual's
  `SQL Assigner Job Plugin <https://spaces.at.internet2.edu/spaces/COmanage/pages/346129582/SQL+Assigner+Job+Plugin>`_
  page for configuration details.
