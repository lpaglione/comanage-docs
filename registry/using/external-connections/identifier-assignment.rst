Identifier Assignment
======================

.. sidebar:: On this page

   .. contents::
      :local:
      :depth: 1


External data rarely arrives with the identifiers your systems need. Your HR
database may know an employee by their employee number, and your collaboration
platform may need an ePPN and an email address — but neither of those identifiers
is going to exist in the source data. **Identifier Assignment** solves this by
automatically generating and assigning identifiers (and email addresses) to
entities in Registry according to rules you define.

Rather than calculating and manually entering identifiers one by one, you
configure one or more Identifier Assignment rules using pluggable algorithms,
and Registry handles the rest: assigning identifiers during enrollment, as part
of a Pipeline sync, or in bulk across all entities in a CO.

For the full technical reference, see
`Registry PE Identifier Assignment <https://spaces.at.internet2.edu/spaces/COmanage/pages/269746372/Registry+PE+Identifier+Assignment>`_
in the Technical Manual.

What Identifier Assignment Can Do
-----------------------------------

A single Identifier Assignment configuration generates identifiers of one type
for entities of one context. Multiple configurations can be combined and
ordered to build up a complete set of identifiers.

**Supported contexts:**

- **People** — the most common context; generate identifiers and email addresses
  for Person records
- **Groups** — generate identifiers for Group records
- *Departments* — not yet implemented

**Output types:** each assignment configuration produces either an Identifier of
a specified type, or an Email Address of a specified type (not both from the
same configuration — use a second configuration if you need both).

Email Addresses generated by assignment are automatically marked as **verified**.

If a Login flag is set on an Identifier Type, generated Identifiers of that type
can be flagged as usable for login to Registry.

Configuring Identifier Assignments
------------------------------------

Identifier Assignments are managed via **Configuration > Identifier Assignments**.

**Context**
   Whether this assignment applies to People, Groups, or another entity type.
   One assignment cannot serve multiple entity types — create separate
   configurations for each.

**Identifier or Email Address Type**
   The type of identifier (or email address) to generate. Registry enforces
   uniqueness per type within a CO.

**Plugin**
   The algorithm to use for generating identifiers. Different plugins implement
   different generation strategies — sequential numbering, format-based
   generation from existing attributes, database lookups, etc.

**Order**
   When multiple assignment configurations should run in sequence — for example,
   generating a username first and then deriving an email address from it —
   use Order to control which configuration runs first. Assignments with lower
   order numbers run first.

   .. note::

      A single assignment configuration can generate either an Identifier or an
      Email Address, but not both. Use two configurations with the appropriate
      Order to generate both from the same source value.

When Identifier Assignment Runs
---------------------------------

Identifier Assignment is triggered at several points in Registry's workflow:

**During an Enrollment Flow**
   The Identifier Assignment Enroller Plugin can be added to an Enrollment Flow
   to assign identifiers as part of the enrollment process.

   .. note::

      Integration with Enrollment Flows is not yet implemented.

**Via a Pipeline**
   Identifier Assignment can run as part of a Pipeline sync, assigning
   identifiers when records are imported from External Identity Sources.

   .. note::

      Pipeline integration is not yet implemented.

**Manually**
   An administrator can trigger assignment on demand by clicking **Assign
   Identifiers** on any entity's canvas page. Registry will assign any eligible
   identifier types that have not yet been assigned to that entity.

**In bulk (Assigner Job Plugin)**
   The Assigner Job Plugin runs Identifier Assignment for all eligible entities
   within a CO at once. Use this after initial setup to assign identifiers to
   existing records, or after adding a new assignment configuration to apply it
   across the CO.

Identifier Assignment can be run multiple times for the same entity without
creating duplicates — if an entity already has an identifier of a given type,
no additional identifier will be created.

Constraints and Uniqueness
---------------------------

Registry enforces the following rules for assigned identifiers:

- Identifiers of a given type must be unique within a CO.
- Uniqueness checks are case-insensitive.
- Uniqueness checks include Suspended identifiers — an identifier that was once
  used and then suspended cannot be reassigned to a different entity.
- An identifier can be reassigned if the original was *deleted* (not merely
  suspended).
- If an entity already has an identifier of a given type, the assignment will
  not create an additional one.

If an Identifier Assignment Plugin cannot construct a valid, available
identifier — for example, because all candidates in a sequence are already taken
— the assignment will fail and no identifier will be assigned. Registry will
note the failure in the logs.

.. note::

   Identifier Assignment currently works best with standard ASCII characters.
   UTF-8 characters are not fully supported.

Changes from v4
----------------

If you are migrating from Registry v4, the following changes apply:

- **The core assignment functionality is now provided by the Format Identifier
  Assignment Plugin**, rather than being built into core code. This means
  identifier generation that previously required no plugin configuration now
  requires installing and configuring the Format plugin.

- **Uniqueness checks now include Suspended identifiers**, preventing
  reassignment of identifiers that were in use and suspended (rather than
  deleted).

- **Email Address uniqueness checks are now scoped to the configured Email
  Address type**, rather than being global across all email addresses.
